## 1. 概念定位

### 1.1 框架位置

**感知接口是框架次循环（行动感知系统）的组成组件，与映射层平级，不隶属于映射层。**

```
次循环（行为感知）：映射层（人格映射 · 决策）⇄ 感知接口（执行）
                                        ⇄ = 唯一合法双向流
```

- 架构依据：architecture.md §6（次循环 = 映射层 + 感知接口）
- 信息流依据：本文件 §2（F1/F2 双向流）

### 1.2 本质：被动能力执行器

**感知接口 = 被动能力执行器（passive capability executor）**，不是决策主体，也不是"智能体"。

- 它的唯一职责：**按调用方给定的参数，执行能力，返回结构化结果**。
- 它**不拥有**任何决策权、推理权、判断权——这些属于框架的**映射层**与外环的"自我迭代顶点"。
- 感知接口是"哑"的执行器。它汇报"做了什么、结果是什么、数据在哪"，但**不说"我觉得"**。任何"思考"都属于上层，不属于此层。

### 1.3 术语收敛（防定位歧义）

> ⚠️ **本文件确立规范称呼，消除多称呼并存**：

| 称呼 | 状态 | 说明 |
|------|------|------|
| **感知接口（Perception Interface）** | ✅ **规范称呼** | 框架次循环组件名，本文件与 architecture.md 统一使用 |
| 感知节点（PerceptionNode） | ⚠️ 实现名 | `scripts/perception_node.py` 的类名/脚本名，指统一入口实现 |
| 治理层 | ⚠️ 别名 | 强调其"治理能力"（trace/校验/可观测）时的称呼 |
| 统一入口层 | ⚠️ 内部路由表述 | 工具箱内部"统一入口层/能力层/兜底层"为**内部路由表述**，不构成框架架构层级（框架层级仅指最外圈/外环/次循环） |

### 1.4 与"节点"概念的区分

| "节点"出现处 | 实际指称 | 层级 |
|-------------|---------|------|
| 三角形顶点节点（得不到/数学/自我迭代） | 主循环三顶点 | 主循环 |
| **感知接口（本组件）** | 次循环组件 | 次循环 |
| 工具节点（toolnode） | 能力层二进制实现 | 感知接口内部 |

**三者不同层：感知接口是次循环组件；toolnode 是它内部的实现（弹药），不是平级组件。**

## 2. 信息流约束

> 与 information-flow.md 第4章「约束总表」一致（本处为感知接口视角的解读）。

### 2.1 合法信息流

| # | 起点 | 终点 | 数据 | 方向 | 依据 |
|---|---|---|---|---|---|
| F1 | 映射层 | 感知接口 | 行动指令（工具名/参数/执行控制） | **双向** | 唯一合法双向流 |
| F2 | 感知接口 | 映射层 | 结构化感知数据 | **双向** | 同上 |
| F3 | 主循环（数学/自我迭代） | 感知接口 | 工具调用请求、调试指令 | 单向进 | - |
| F4 | 感知接口 | 主循环 | 清晰无噪音数据 | 单向出 | - |
| F5 | 感知接口 | 记录层（错误智慧库） | 错误事件上报 | 单向出 | 上报≠入库 |
| F6 | 感知接口 | 能力层（toolnode/busybox） | 子命令调用 | 内部 | 工具箱内部路由，非框架层信息流 |

### 2.2 禁止的信息流

| ❌ 禁止 | 原因 |
|---|---|
| 感知接口 → 记录层 JSON 轨直接写库 | 记录层数据只来源于三顶点 |
| 感知接口 → 最外圈（意向性模组） | 最外圈只与建议池交互 |
| 感知接口主动发起调用 | 被动执行器：调用与否由映射层决定（红线一） |
| 感知接口对结果做语义判断/二次决策 | 只能按预置规则机械响应（红线一） |
| 感知接口修改调用方意图（"我以为你想要的"） | 红线一 |

### 2.3 信息流验证流程

```
步骤1：识别起点 / 终点 / 数据类型 / 方向
步骤2：在 §2.1 表中查找——合法则继续，非法则拒绝
步骤3：检查 §2.2 禁止清单——命中则拒绝
步骤4：实现代码时添加强制标注（发送者/接收者/数据类型/方向）
```

## 3. 统一契约与治理能力

### 3.1 统一契约格式

所有经感知接口的数据交换必须遵循统一契约：

```json
{
  "status": "success|error",
  "data": { },
  "error": null,
  "metadata": { "duration_seconds": 0.12, "trace_id": "..." },
  "trace_id": "...",
  "timestamp": "2026-08-12T00:00:00"
}
```

### 3.2 契约约束（C1-C5）

| # | 约束 | 说明 |
|---|---|---|
| C1 | trace_id 全链路贯穿 | 每次调用由 PerceptionNode 生成并强制注入，toolnode 尊重注入值 |
| C2 | 参数 schema 单一事实来源 | `TOOL_REGISTRY` 收归全部 schema，调用前强制校验 |
| C3 | 防静默失败 | 写入类 → 回读磁盘确认，返真实路径+字节+sha256；检索类 → 返来源 mtime（非响应时刻） |
| C4 | 边界归一化 | toolnode/busybox 的 status-based 契约 → PerceptionNode 内部 success-based，边界统一转换 |
| C5 | 错误契约不误判崩溃 | 合法 JSON 错误契约（如 COMMAND_TIMEOUT）按业务结果处理；仅 stdout 非合法契约时才视为崩溃 |

### 3.3 治理能力清单

| 能力 | 实现 |
|---|---|
| Trace ID 全链路 | 每次调用生成并强制注入，toolnode 尊重注入值 |
| 参数校验 | Schema 单一事实来源（TOOL_REGISTRY），缺参/未知 op → INVALID_PARAMS |
| 缓存策略 | ToolCache 执行态复用（get/set/clear） |
| 重试机制 | `_no_retry` 确定性错误码集合，预算内机械重试 |
| 可观测性 | total/success/fail/cache/retry 指标导出（get_metrics） |
| 错误台账 | 内部状态支撑重试判定；错误事件上报记录层（上报≠入库） |
| 流式响应 | call_tool_with_streaming（SSE 模拟） |
| 分页支持 | search_documents 预留 |
| Token 预估 | 内置能力 |
| 版本控制 | ToolConfig + 契约版本 |

### 4.1 工具注册表（TOOL_REGISTRY · 5 项）

### 4.2 toolnode 子命令（23 个操作）

| 组 | 操作 | 说明 |
|---|---|---|
| **fs**（9） | read / write / list / copy / move / delete / mkdir / stat / search | 文件系统全操作；写入回读验证 + 来源时间戳（防静默失败） |

### 4.3 能力边界（诚实声明）

- 3 个 STUB 桩工具未实现（web_search / get_weather / search_documents）
- 感知接口是**被动执行器**：不决策、不推理、不主动发起调用（红线约束，见 §5）
- C 扩展双平台（.pyd / .so），加载失败自动降级纯 Python
- BusyBox 能力边界：fs 核心 + proc.list + sys.all + exec.run；不支持 → BUSYBOX_UNSUPPORTED

## 5. 红线约束（被动能力执行器 · 不可逾越）

> **红线总纲（先读这条）**："完全无自主推理"约束的只是感知接口的**语义思考**（对结果的"意味着什么、下一步怎么办"的研判），**不是**禁止它处理错误。错误处理的关键不在"想"，而在"报得清楚 + 查表准确"：
> - **执行态错误处理**（感知接口拥有，红线内允许）：确定性错误码识别、查 `_no_retry` / `retryable` 表、预算内机械重试、结构化错误契约上报——本质是 if-else + 查表，不是思考
> - **语义态错误决策**（主循环/映射层专属）：理解上下文、分析根因、决策降级路径（换工具/降精度/上报人工）、是否入库——需要全局视野与历史经验，属于思维
> - **学习闭环**（记录层专属）：错误入库 → 根因分析 → 生成预防规则 → 下次调用前前置检查
>
> 三层分工是错误处理的**完整形态**。若让感知接口"自主推理"，它只能看到局部（无上下文/无历史/无人格），产生的是**残缺思考**，比机械响应更危险，且会架空主循环、断裂学习闭环。**红线不是在约束能力，是在防止降级。**

### 5.1 红线一：禁止自主推理与决策

- ❌ 不决定"该不该调用某工具"
- ❌ 不对结果做语义判断或二次决策（"这个结果不对，我应该重试/换个工具"——不允许）
- ❌ 不修改调用方意图
- ❌ 不跨环伸手（不替记录层/自我迭代做进化/复盘/智慧库写库等决策）
- ✅ 允许：按**预置规则**机械响应（`_no_retry` 集合、确定性错误码、`retryable` 标志、预算内重试）——这是执行态能力，不是语义思考

### 5.2 红线二：最小化自我表述

- ✅ 只输出结构化契约 + operational telemetry（trace_id / backend / duration）
- ✅ 进程内 logger 可输出执行态日志（`using rust backend`），不进入契约
- ❌ 禁止"我认为/我决定/我治理/我进化"等主体性措辞
- ❌ 禁止对调用方解释超出错误码+消息范畴的原因

> **适用范围声明（防定位歧义）**：本章全部红线约束的对象**仅是感知接口（工具层）**，不适用于智能体整体（主循环/映射层）与用户的对话输出——智能体整体在对话中当然可以（且应当）表达观点、解释原因、进行反思。工具层红线与智能体整体的对话行为是两个层面，切勿将"工具不说'我觉得'"误读为"智能体不能说'我觉得'"。

### 5.3 红线三：错误台账归属

- ✅ 感知接口内部可维护**只读错误台账**（支撑重试判定与可观测）
- ✅ 可向上层智慧库接口**上报**错误事件（单向依赖、不反向约束）
- ❌ 台账不得被宣称为框架"错误智慧库"的写入动作
- ❌ 入库/复盘/预防决策在记录层完成，感知接口不参与

## 6. 错误处理分层

> 本细则消除"无自主推理 = 无错误处理能力"的误解。错误处理是三层分工的闭环，任何一层缺失都是残缺的错误处理。

### 6.1 执行态错误处理（感知接口拥有 · 红线内允许）

| # | 能力 | 实现形态 | 边界 |
|---|---|---|---|
| E1 | 确定性错误码识别 | 查 `_no_retry` 集合（COMMAND_TIMEOUT / DANGEROUS_COMMAND_BLOCKED / BUSYBOX_* 等） | 只识别、不解释"为什么" |
| E2 | 预算内机械重试 | 按预置规则（格式/参数失败 2 次立即重试；超时指数退避 1s/2s/4s；语义错误 2 次带反思轨迹） | 预算由上层预置，感知接口只执行 |
| E3 | 结构化错误契约上报 | 错误码 + message（事实级描述）+ trace_id + metadata | 上报 ≠ 入库；不携带建议性/叙事性内容 |
| E4 | 兜底路由触发 | 按 §7 触发条件机械判断（B1-B4） | 触发与否是查表，不是判断 |
| E5 | 防静默失败 | 写入回读验证、检索返来源时间戳 | 验证动作，非语义判断 |

**判据**：一项动作是否属于执行态，看它是否满足"**输入确定性错误信号 → 查表/规则 → 输出确定性响应**"。满足即为执行态（允许）；不满足即为语义态（禁止）。

### 6.2 语义态错误决策（主循环 / 映射层专属）

| # | 决策 | 归属 | 说明 |
|---|---|---|---|
| S1 | 根因分析 | 主循环（数学顶点） | "为什么失败"需要上下文与推理 |
| S2 | 降级路径选择 | 主循环 / 映射层 | 换工具 / 降精度 / 上报人工——需要全局视野 |
| S3 | 是否入库 / 复盘 / 预防 | 记录层 | 聚合多源错误后决策（红线三） |
| S4 | 调整重试预算 | 上层（自我迭代顶点） | 感知接口只消费预算，不修改预算 |
| S5 | 人格化处理错误 | 映射层 | 基于马斯洛需求 × 大五人格的决策 |

**感知接口在该层的角色**：只提供**足够结构化**的错误信息，让上层能快速决策——"报得清楚"本身就是它的核心价值。

### 6.3 学习闭环（记录层 · 错误智慧库）

```
错误发生
  → 感知接口执行态处理（E1-E5）
  → 结构化上报（E3）
  → 记录层：入库 → 根因分析 → 生成预防规则（Phase 3 规则自动生成）
  → 预防规则回流 → 下次调用前前置检查（error_wisdom_prevention）
```

- ✅ 感知接口受益于预防规则（前置检查减少错误），但**不参与**规则生成
- ✅ 错误从"临时处理"进化为"系统预防"——这是三层分工独有的优势

### 6.4 红线边界示例（可执行判断）

| 场景 | 感知接口该做 | 感知接口禁止做 |
|---|---|---|
| toolnode 返回 COMMAND_TIMEOUT | 查 `_no_retry` → 不重试 → 上报错误契约 | 自行决定"换 exec 用 bash 重试" |
| fs.write 回读不一致 | 返回 verified=False + 错误契约 | 自行决定"重写一次或换路径" |
| 工具连续失败 3 次 | 按预置规则上报，附 trace_id 与失败次数 | 自行决定"放弃该工具，改用备用工具" |
| 参数校验失败 | 返 INVALID_PARAMS（schema 规则） | 自行推断"用户想要的参数"并改写 |

## 7. 兜底路由（三级）

```
主路径（Rust 二进制 toolnode）→ 回退（Python 原型 toolnode.py）→ 保命（BusyBox）
```

| # | 触发条件 | 兜底动作 |
|---|---|---|
| B1 | `_toolnode_binary_path()` 返回 None（Rust + Python 都缺） | 直接 BusyBox |
| B2 | subprocess spawn 失败 / 超时（OSError/TimeoutExpired） | BusyBox |
| B3 | stdout 非合法契约（非 JSON / 无 status） | BusyBox |
| B4 | 合法错误契约（exit 1 + 合法 JSON） | **不**触发兜底（业务结果） |

**约束**：
- ✅ BusyBox 能力边界须明确（不支持的操作返 `BUSYBOX_UNSUPPORTED`，不静默假装成功）
- ✅ BusyBox 契约与主路径一致，`metadata.backend="busybox"` 标记可观测
- ✅ 确定性错误（COMMAND_TIMEOUT 等）进 `_no_retry` 集合，不盲目重试

## 9. 工程实现与验收（工具节点重规划）

### 9.1 背景与目的

当前 `scripts/` 下 4 个散装 CLI（`cli_file_operations` / `cli_system_info` / `cli_process_manager` / `cli_executor`）存在三个结构性问题：

1. **脆弱**：Python 脚本依赖解释器 + 第三方库（如 `psutil`），环境异常即整层归零。
2. **裸奔**：完全绕开 PerceptionNode 统一入口层（`import TraceContext` 却从未调用，是死代码），无 trace_id / 重试 / 缓存 / 可观测 / 错误台账。
3. **重复**：能力是系统命令子集，且重复 harness 已提供的 Read/Write/Glob/Grep/Bash。

**目的**（用户定调）：在**难以处理的局面下以最标准的姿态顺利推进难题与效率**；内部快速自用，使内部工具调用**比 harness 更强**，达成"**一个统一入口即最优解**"。

### 9.2 设计原则（由 BusyBox 优势推导）

| # | 原则 | 含义 |
|---|---|---|
| P1 | 统一入口 | 单一工具节点取代散装 4 CLI，避免切换成本 |
| P2 | 零/最小依赖 | 核心命令自包含，最恶劣环境也能自举 |
| P3 | 统一契约 | 所有节点贯穿：JSON 返回 + trace_id + 参数 schema |
| P4 | 分级兜底 | 主路径(精炼节点) → 统一入口(报错回退) → BusyBox(保命) |
| P5 | 自我进化 | 调用失败/异常自动入智慧库，闭环复盘 |

### 9.3 目标拓扑（三级路由）

```
调用方（智能体 / 外部 API）
    │ call_tool(node, args)
    ▼
PerceptionNode · 统一入口层（Python，保持）
【被动能力执行器 · 无自主推理】
trace_id · 预防检查 · 缓存 · 重试 · 可观测 · 错误台账 · TOOL_REGISTRY
    │ subprocess / FFI
    ▼
工具节点 · 主路径能力（Rust 静态二进制 toolnode）
fs/sys/proc/exec 四组 · 零依赖 · 快启动 · 内存安全 · 跨平台
    │ 失败 / 二进制缺失 · 兜底
    ▼
BusyBox · 保命兜底（纯 stdlib 子集）
```

> 说明：此"三级"是**工具节点单一能力内部**的主路径/回退/保命路由，**不是**框架宏观"三层架构"（最外圈/外环/次循环）。感知接口整体属于框架次循环的"感知接口（Tool Use）层"。

### 9.4 实现语言策略

| 路由角色 | 语言 | 理由 |
|---|---|---|
| 主路径能力（工具节点） | **Rust → 静态二进制** | 零依赖、快、内存安全、跨平台，恶劣环境可自举 |
| 统一入口层（PerceptionNode） | **Python（保持）** | 逻辑复杂、需快迭代，调 Rust 二进制即可 |
| 保命兜底（BusyBox） | 纯 Python 标准库（内嵌进程） | Rust + Python 原型缺失/损坏时保命 |

- **构建目标**：`x86_64-pc-windows-gnu` / `x86_64-unknown-linux-gnu`（macOS 待定）
- **跨平台双二进制**：Windows PE `toolnode.exe`（1.6MB）+ Linux ELF `toolnode`（941KB），运行时按平台感知选择，与 C 扩展 `.pyd`/`.so` 双平台策略同构
- **已知约束**：Rust 节点经 Python 统一入口层 `subprocess` 调用，Python 仍在链路一环；彻底"脱离 Python 自举"需统一入口层也 Rust 化（未来可选）

### 9.5 落地步骤

| 步 | 内容 | 产出 | 可回退 | 状态 |
|---|---|---|---|---|
| 1 | 精炼：4 CLI 合并为统一 `toolnode` 入口（先 Python 原型） | 统一入口 + 契约验证 | 删原型即回退 | ✅ 完成 |
| 2 | 接治理：注册进 `TOOL_REGISTRY`，trace_id/重试/缓存/智慧库生效 | 治理层有活可干 | 取消注册即回退 | ✅ 完成 |
| 3 | Rust 化：核心用 Rust 重写编译静态二进制，替换 Python 原型 | 零依赖主路径 | 切回 Python 原型 | ✅ 完成 |
| 4 | 兜底：PerceptionNode 路由加 BusyBox fallback 分支 | 保命层就位 | 去分支即回退 | ✅ 完成 |
| 5 | 验证：健康检测 + 端到端（调用→trace→重试→智慧库） | 验收报告 | — | ✅ 完成 |

### 9.6 与 harness 的边界

- **用本层**：需标准化姿态、可观测/可追溯、失败要进错误台账、或恶劣环境下需自举的操作。
- **直接用 harness Bash**：一次性、无需追踪的简单操作。
- 本层不强在"替代 harness"，而强在"标准姿态 + 入口路由 + 兜底"——与 harness 互补而非重复。

### 9.7 构建记录与验收（步骤 1-5）

#### 修复的三个边界 bug（均为"契约/退出码错位"类，正是 Q4/Q6 要防的静默失败）

1. **契约主键错位（根因 blocker）**：toolnode 输出 `status`-based 契约，PerceptionNode 内部约定 `success`-based；`_execute_toolnode` 原样透传导致 `call_tool` 把 `success=None` 误判失败。修复：边界归一化（含 error 形状对齐、trace_id 强制一致）。
2. **退出码误杀错误契约**：toolnode 失败时把错误契约写进 stdout，原实现 `returncode != 0` 直接 raise，把合法的 COMMAND_TIMEOUT 当崩溃丢弃。修复：先按 stdout 解析契约，仅当 stdout 非合法契约时才视为真实崩溃。
3. **（连带）Windows 换行符静默改写**：fs.write 文本模式 `"w"` 在 Windows 把 `\n` 翻成 `\r\n`，回读不一致。修复：改二进制写入，保证写入字节 == 回读字节。

#### 验收结果

**Step 2 门禁（10/10 通过）**：Q1 真实接线 ✅ / Q1 桩工具拦截 ✅ / Q2 参数校验 ✅ / Q3a+b trace_id 贯穿 ✅ / Q4a 写入回读验证 ✅ / Q4b 来源时间戳 ✅ / Q5 确定性错误不重试 ✅ / Q6 失败入智慧库 ✅ / Q+ 危险命令拦截 ✅

**Step 3 Rust 化复测（10/10）**：Q1-Q6 + Q8 跨 Rust 二进制一致（data_keys 含 rust 标记）

**Step 4 BusyBox 兜底（8/8）**：F8 正常路径不误触发 / F1-F4 核心能力 / F5 危险拦截 / F6 不支持明确报错 / F7 trace_id 贯穿

**Step 5 端到端终检（13/13）**：Q1-Q8 全通过 + 危险网关

> **验收体系说明（防定位歧义）**：Q1–Q8 端到端验收（13/13）为**感知接口专项验收**（工具层权威基线）；项目级全流程验收见根目录 TEST_REPORT.md（76/76）。两套体系并行且互不替代。

## 10. 工具调用工程规范（行业通用参考）

> 📄 来源：原 tool_use_spec.md（通用规范部分）。本节为行业通用的 Tool Use 工程规范，非框架特有——**框架特有约束以第1-9章为准**。

### 10.1 工具定义格式

```json
{
  "name": "get_current_weather",
  "description": "获取指定城市的实时天气信息",
  "parameters": {
    "type": "object",
    "properties": {
      "location": {"type": "string", "description": "城市名称"},
      "unit": {"type": "string", "enum": ["celsius", "fahrenheit"]}
    },
    "required": ["location"],
    "additionalProperties": false
  },
  "strict": true,
  "version": "1.0.0",
  "cacheable": true,
  "estimated_tokens": 200
}
```

**命名规范**：snake_case，`^[a-zA-Z_][a-zA-Z0-9_-]{0,63}$`，语义清晰（`search_product` 优于 `do_stuff`）。

### 10.2 设计原则

- **单一职责**：多功能聚合是错误（`query_service` ❌）；独立拆分（`get_weather` / `get_stock_price` / `search_news` ✅）
- **幂等性**：相同输入 → 相同输出，避免重试导致重复副作用
- **参数校验前置**：所有外部输入必校验
- **Strict Mode**：`strict: true` + `additionalProperties: false` = 100% Schema 合规，生产环境标配

### 10.3 标准化输出格式

**成功响应**：
```json
{
  "success": true, "status": "success",
  "data": {"temperature": 25, "condition": "sunny"},
  "metadata": {"tool_name": "get_weather", "execution_time_ms": 127, "timestamp": "2024-01-01T00:00:00Z", "trace_id": "trace_abc123"}
}
```

**错误响应**：
```json
{
  "success": false, "status": "error",
  "error": {"code": "CITY_NOT_FOUND", "message": "城市'XYZ'未收录", "retryable": false},
  "metadata": {"tool_name": "get_weather", "timestamp": "2024-01-01T00:00:00Z", "trace_id": "trace_abc123"}
}
```

### 10.4 流式响应（SSE）

长时间执行的工具使用 Server-Sent Events 提供实时进度反馈：

| 事件类型 | 说明 | 触发时机 |
|----------|------|----------|
| `tool_progress` | 工具执行进度 | 长时间任务执行中 |
| `tool_result` | 工具执行成功结果 | 执行完成且成功 |
| `tool_error` | 工具执行错误 | 执行失败或异常 |
| `tool_retrying` | 重试通知 | 遇到可重试错误时 |

**集成建议**：快速工具（<1s）使用 HTTP 响应；长时间工具自动切换 SSE；记录每个事件的 trace_id。

### 10.5 复杂数据处理

**分页机制**（游标分页避免上下文溢出）：
```json
{"items": [...], "pagination": {"has_more": true, "next_cursor": "eyJvZmZzZXQiOjEwfQ==", "total_count": 100}}
```

**文件与二进制**：小文件（<1MB）Base64 编码；大文件（≥1MB）预签名 URL。

**大响应截断**：超过上下文窗口时提供截断策略或摘要机制（`truncated: true` + `truncation_info`）。

### 10.6 错误处理与重试

| 错误码 | 含义 | 处理建议 |
|--------|------|---------|
| INVALID_PARAMS | 参数验证失败 | 检查参数类型和格式 |
| RESOURCE_NOT_FOUND | 资源不存在 | 确认资源ID或路径 |
| PERMISSION_DENIED | 权限不足 | 检查授权 |
| TIMEOUT | 执行超时 | 重试或优化 |
| RATE_LIMITED | 超出速率限制 | 延迟后重试 |
| NETWORK_ERROR | 网络错误 | 重试 |
| EXECUTION_ERROR | 执行错误 | 检查日志 |
| QUOTA_EXCEEDED | 配额超限 | 升级计划 |

**重试规则**：网络错误最多 3 次指数退避；超时最多 2 次；速率限制按 Retry-After 延迟；参数/权限/配额错误不重试。

### 10.7 可观测性

**Trace ID 全链路追踪**：所有工具调用必须包含 `trace_id`，用于关联整个推理链路。

**监控指标**：

| 指标 | 说明 | 告警阈值 |
|------|------|---------|
| 调用成功率 | 成功调用数 / 总调用数 | < 95% |
| 平均响应时间 | 所有调用的平均耗时 | > 500ms |
| P99 响应时间 | 99% 调用的耗时 | > 2000ms |
| 错误率 | 错误调用数 / 总调用数 | > 5% |
| 重试率 | 重试调用数 / 总调用数 | > 10% |

### 10.8 版本控制与上下文管理

**语义化版本**：`MAJOR.MINOR.PATCH`；参数变更必须向后兼容（新增参数提供默认值，不删除已有参数）。

**废弃策略**：`deprecated: true` + `sunset_date` + `replacement` + `migration_guide`。

**Token 预估**：`estimated_tokens`（纯文本 ÷4、JSON ÷3.5、代码 ÷2、Markdown ÷3.5）。

**缓存策略**：`cacheable: true` + `cache_ttl` + `cache_key_params`（缓存键只含关键参数）。
